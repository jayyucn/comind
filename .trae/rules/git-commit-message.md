# Git Commit 提交信息规范

## 标准格式

```
<类型> <模块>: <具体变更描述>

<详细说明（可选）>
```

## 类型标识

| 类型 | 说明 | 适用场景 |
|------|------|----------|
| 新增 | 添加新功能或模块 | 新页面、新组件、新API接口 |
| 修复 | 修复bug或问题 | 功能异常、错误处理、兼容性问题 |
| 优化 | 性能或体验优化 | 加载速度、响应时间、交互流畅度 |
| 重构 | 代码结构调整 | 代码整理、架构优化，不影响功能 |
| 文档 | 文档更新 | README、注释、技术文档 |
| 测试 | 添加或修改测试代码 | 单元测试、集成测试、E2E测试 |
| 配置 | 配置文件变更 | 构建配置、环境变量、依赖版本 |

## 核心规则

### 1. 语言要求
- 必须使用中文编写
- 确保团队成员理解一致
- 避免使用专业术语缩写

### 2. AI友好格式
- 使用标准的 `<类型> <模块>: <描述>` 格式
- 类型标识固定，便于自动化工具解析
- 模块名称使用项目中统一的命名

### 3. 长度控制
- 主题行长度控制在 50-72 字符之间
- 正文每行不超过 80 字符
- 使用空行分隔主题行和正文

### 4. 关键信息前置
- 将最重要的变更内容放在开头
- 类型和模块信息优先展示
- 具体描述突出核心变更点

### 5. 描述要求
- 反映代码变更的实际意图，而非实现细节
- 使用明确动词，避免模糊词汇
- 清晰阐述变更内容和目的

## 正例与反例

### 正确示例
```
修复 用户登录: 处理手机号格式校验异常
新增 首页组件: 添加轮播图自动播放功能
优化 数据加载: 减少API请求次数提升页面响应速度
重构 用户模块: 提取公共验证逻辑至工具函数
```

### 错误示例
```
修复bug                                  # ❌ 缺少模块和具体描述
改进一些东西                              # ❌ 使用模糊词汇"改进"
调整登录页面的样式                        # ❌ 使用模糊词汇"调整"
新增一个很重要的功能                      # ❌ 描述模糊不清
修改了用户模块的一些代码实现细节            # ❌ 描述实现细节而非意图
```

## 完整示例

### 示例1：简单修复
```
修复 用户注册: 修复密码强度校验失败问题
```

### 示例2：带详细说明
```
优化 商品列表: 实现虚拟滚动提升渲染性能

- 列表项超过100条时启用虚拟滚动
- 减少DOM节点数量约80%
- 滚动流畅度提升至60fps
```

### 示例3：重构
```
重构 订单模块: 拆分大型组件提升可维护性

- 将OrderDetail拆分为5个子组件
- 提取公共逻辑至composables
- 添加组件间通信类型定义
```

## 注意事项

- 每次提交应只包含一个逻辑变更
- 提交信息应能帮助代码审查者快速理解变更
- 避免在提交信息中使用表情符号或特殊字符
- 模块名称应与项目目录结构或功能模块保持一致
