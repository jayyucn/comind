# 技术文档总结（2026-07-17 至 2026-07-19）

## 一、DateRef 数据库表改造（核心架构升级）

### 目标
将前端内存索引 `DateRefIndex` 下沉为 `comind-core` 的 `DateRef` 物化表，实现写入即维护，消除手动同步漂移。

### 架构设计
- **派生数据落 `comind-core`**：共享 SQLite，桌面/网页共用同一张表
- **写入即维护**：hook 进 `BlockService::create/update/delete`，不再依赖前端手动调用
- **替换而非叠加**：前端退役内存索引，改查数据库

### 核心实现
1. **Schema**（`sqlite.rs` + `sqljs.rs`）：`DateRef` 表 + 索引 `idx_date_ref_kind_day` / `idx_date_ref_block`
2. **类型**（`types/date_ref.rs`）：`DateRef` 结构体，含 `date_day` 派生列（用于范围查询）
3. **Repository**（`repository.rs`）：`DateRefRepository` trait + `StorageAdapter::date_refs()` 访问器
4. **Service**（`services/date_ref_service.rs`）：
   - `extract_date_refs`：Rust 正则解析（语法唯一事实来源）
   - `sync_date_refs_for_block`：删旧插新，hook 进 block 写入路径
   - `query_by_date_range` / `query_overdue`：范围/逾期查询
   - `rebuild_all`：历史数据回填（幂等）
5. **BlockService 接入**：`create/update/delete` 统一调用 `sync_date_refs_for_block`
6. **FFI 暴露**：Tauri 4 条命令 + wasm 4 个绑定
7. **前端切换**：`useDateRefIndex.ts` 改服务端查询，删除 `date-ref-index.ts` 内存实现

### 状态
- ✅ Phase A（Rust 端）：已完成并通过编译验证
- ✅ Phase B（FFI + 前端切换）：已完成
- ⚠️ Web 端 wasm 构建：被 pre-existing 的 `SqlJsAdapter` 缺 `notifications` 访问器阻塞（非本次引入）

## 二、通知系统 Bug 修复（2026-07-19）

### 修复 1：角标数字单调递增
**根因**：`fireNotification` 对非 `pending` 状态仍创建新通知，每次 scheduler 触发都新建一条。
**修复**：`findExistingNotification` 找到任何已存在通知都直接返回，不再重复创建。

### 修复 2：角标数字虚高（刷新后 3、点开变 1）
**根因**：`triggerCheckAndFire` 用累加逻辑 `unreadCount.value++`，每次触发都虚增。
**修复**：去掉累加，改为 fire 循环后调用 `refreshUnreadCount()` 从 DB 重算。

### 修复 3：点"全部已读"后刷新仍有数字
**根因**：`markAllRead` 仅本地置 0，未从 DB 重算。
**修复**：末尾改 `await refreshUnreadCount()`。

### 修复 4：修改 block 内容后通知不更新
**根因**：命中 `existing` 时直接返回，从不回写 payload。
**修复**：
- 抽出 `buildPayload` 复用 payload 构造
- `unread`/`read` → 回写最新 payload
- `pending` → 回写后转 `unread`
- 新增 `updateNotificationPayload` 全链路（Rust trait + Tauri command + TS 包装）

### 修复 5：删除通知后复活
**根因**：
1. `fireNotification` 对 `dismissed` 也 `return existing` → 回灌内存
2. `delete_older_than` 物理删 `dismissed` → 锚点消失后重建
**修复**：
- `dismissed` → `return null`（不再重建）
- `delete_older_than` 只清 `status = 'read'`，永久保留 `dismissed` 作去重锚点

### 修复 6：删除后仍显示在列表
**根因**：软删只改 status，未从内存数组移除；`sortedNotifications` 未过滤 `dismissed`。
**修复**：
- `sortedNotifications` 增加 `.filter(n => n.status !== 'dismissed')`
- `deleteNotification` 直接 `splice` 移除 + `await loadNotifications()` 双保险

### 修复 7：删除按钮改为软删除
**根因**：物理删除后 `checkAndFire` 找不到锚点 → 重新创建。
**修复**：删除走 `service.dismiss`（`status = 'dismissed'`），保留记录作去重锚点。

### UI 调整
- 移除"忽略"按钮，保留"删除"
- 列表项按钮：「标记已读 / 稍后提醒 / 删除」

## 四、关键设计决策

| 决策 | 说明 |
|------|------|
| DateRef 作为单一派生源 | Notification 从 DateRef 表读取，不再解析 content |
| 软删除（dismissed） | 保留物理记录作去重锚点，防止通知复活 |
| 写入即维护 | 只在 `BlockService` 一处维护派生数据，消除漂移 |
| 回填幂等 | `rebuild_all` 先删后插，可重复执行 |
