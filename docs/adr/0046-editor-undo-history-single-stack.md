## Context

原始诉求（对话，2026-09-14）：

> 页面级建立快照式撤销历史栈，Ctrl+Z / Ctrl+Shift+Z（兼容 Ctrl+Y）统一回退「结构操作 + 文字」，防误操作丢数据、补齐 Notion/Logseq 体验。

### 前提核查（载体断言 vs 代码现状）

| 断言 | 核查结果 | 证据 |
|---|---|---|
| 「现在没有撤销，要从零建」 | **半真**：全局栈确实 0 命中，但**块内文字撤销已经存在**（TipTap v3 `UndoRedo`，StarterKit 默认启用）。所以不是「从零建」，而是「要不要把已有的那个拆掉」 | `src` 下 `undoStack\|redoStack\|useUndo\|useHistory` 0 命中；`Editor.vue:79-91` 未传 `undoRedo:false` |
| 「非编辑态 Ctrl+Z 无反应」 | **成立**（观测） | `BlockList.vue:278-353 handleDocKeyDown` 只分派 Backspace/Delete/Ctrl+X/V/Escape/Enter/Tab/Ctrl+C；`useGlobalHotkeys.ts` 只管 k/g/i/b/t；无任何 `key==='z'\|'y'` 分支 → 落 WebView 默认 |
| 「撤销/重做是本阶段该做的」 | **可疑：诉求疑似照着过期草案写的** | `docs/3-features/functional-design-spec.md:96,200,379` 引用的 `useUndo` / `useHistory.pushState()` **在 `src` 里不存在**（遗留草案）；`docs/4-ui/interaction-spec.md:1039` 把它列为 **「Phase 2 考虑」**、`docs/active/spec.md:177` 只有未勾选框 → 它是被**有意推迟**的，不是被忘了 |
| 「防误操作丢数据」 | 现象有实证，但**归因是推测**：`deleteSelected` 作用域是全部 `anchorIds`、**无软删**（曾误删 8 块靠 comind.db + WAL 雕刻恢复）；然而「撤销栈能防住它」无证据 —— 撤销栈只在用户**察觉了并去按 Ctrl+Z** 时才救人 | `memory/2026-09-13.md`；该动机经 ADR-0047 D2 **转由回收站承接** |
| 「统一回退结构+文字」 | **原表述自相矛盾**：抢 Ctrl+Z 的是**两个块私有栈**（TipTap / CodeMirror），且都随编辑器卸载销毁 → 不做单一权威栈，字面上的「统一」不成立 | 上图三落点；`Editor.vue:250-272` `destroy()` |
| 「快照式」 | **术语已有主**：ADR-0042 的 `Snapshot` / `page_snapshots(page_id,date,version,content_json)` 是 **Ideas 物化快照**，与编辑器撤销无关，同名不同义 | `CONTEXT.md` → Snapshot (页面快照) |

**载体没写、但改变影响面的两条约束**：

1. **store 没有「一次用户动作 = 一次提交」的收口** —— `src/stores/blocks.ts` 有 15+ 个 async 写方法（`createBlock:586`、`mergeBlockInto:1009`、`applyTextRangeDeletion:1166`、`indent:1192`、`deleteBlocks:1258`、`updateBlockContent:1358`、`pasteBlocks:1449`…），一次 indent / merge 常触发多次写入。天然事务边界只在 Rust 侧（`crates/comind-core/src/services/block_write.rs`；`save_block_tree` / `execute_batch` 各一事务，ADR-0019 Q4/Q7）。
2. **文字写入夹了 300ms debounce**（`Editor.vue` `debouncedEmitSave` → `Block/index.vue:540` → `useBlockEditorLifecycle.ts:94-103`）—— 粒度能否稳，取决于这条路径。

### 本质需求

> **在同一页面内，`Ctrl+Z` / `Ctrl+Shift+Z`（含 `Ctrl+Y`）是唯一且语义稳定的反悔接口** —— 任何焦点下都退「用户心里的上一步」；一步的切分单位是**用户的输入突发**（≈500ms 停顿封口）；覆盖面是**全部文档内容与结构变更**，不退视图噪声；栈在**会话内**、上限 100–200 步。

### 为什么「快照式」不是目标（反证）

页面快照、op-log、反向命令（undo command pattern）—— **三种完全不同的机制都能满足同一目标**，故机制是实现手段，行为才是需求本身。另两条反证：软删/回收站只救「删除」这一类，救不了「缩进错了 / 移动错了」；确认弹窗能让人敢操作但会打断，不满足「试错无摩擦」。⇒ 目标提炼正确，上一层的原始动机是「**让编辑器可以被试探着用**」。

## Decision（grill-up 2026-09-14 锚定；grilling 2026-09-14 补 D8–D11 并修订 D4）

| # | 决策点 | 裁定 |
|---|---|---|
| D1 | **根是哪一个** | **「Ctrl+Z 语义稳定可预期」**。原始诉求绑了三个动机（防丢数据 / Notion 手感 / 消除「块内可撤、结构不可撤」的割裂），裁定只收「预期一致」为根；「Notion 手感」被它吸收；「不再丢数据」**明确降级、移出本锚点** —— 撤销栈救不了「没察觉就关掉 App」，该动机转由**回收站**承接（ADR-0047 D2）。 |
| D2 | **Ctrl+Z 归属** | **统一栈全权接管**：禁用 TipTap / CodeMirror 内置历史，块内文字也进同一个栈。这是 Notion/Logseq 的做法，也是「统一」唯一自洽的解。**否决**「分层：编辑态内编辑器优先」——两个栈叠加会产生「撤销穿越焦点」的怪行为（块内撤一半、退出块再按 Ctrl+Z 跳到结构操作，中间那些文字步骤永远够不着）。 |
| D3 | **粒度** | **输入突发 + 停顿**：连续输入算一步，停顿（≈500ms）或焦点变化后封口。现有文字落库已是 300ms debounce，阈值接近，但**结构操作之间要显式封口**（一次 indent 连带子树多次写入必须折叠成一条）。 |
| D4 | **不进栈的边界**（2026-09-14 修订） | **视图状态三分法** —— ① 用户**主动**做的（折叠 toggle、块类型切换）→ **入栈**；② 由结构操作**派生**的视图变化（缩进进折叠父块时自动展开父块，ADR-0045 D4）→ **随该操作一起回滚**；③ 纯噪声（选区 / 光标 / 滚动 / 页面切换、页面级删除/重命名）→ **不进栈**。<br>**修订理由**：原表述「折叠一律不进栈」把 ① 与 ② 混为一类，后果是用户**有意**折叠后按 `Ctrl+Z`，栈顶不是折叠而是他 10 秒前打的字 —— `Ctrl+Z` 会「跳过用户刚做的那一步」，正是 D4 想消灭的体验；同时 ② 不回滚会让「撤销后视图与操作前不一致」。 |
| D5 | **栈的寿命与容量** | **会话内内存栈**，重开 app 即清；容量按**字节预算 32 MB**（超限裁最旧）而非固定步数 —— 真机 slim 快照 ≈270 B/块，最大页（84 块）200 步仅 **4.4 MB**，故真实语料下几乎永不裁剪，仅在极端大页（>1000 块）生效。**否决持久化到 DB** —— 这不是保守取舍，而是**结构性必然**（机制与寿命耦合，见下节「机制与寿命的耦合」）。 |
| D6 | **作用域** | **页面隔离**（切页各一套栈），且**不复用 `page_snapshots` 表、不占用「快照」一词**。**否决**全局单栈。非主文档区的编辑器（BlockModal / 任务中心卡片）**归所属页面**，弹窗不是新作用域。 |
| D7 | **交付切分** | **一次做完，不要中间态**：直接奔单栈最终态，避免「撤销穿越焦点」的中间行为被用户记住。**（此条 Jay 的选择与推荐相反 —— 推荐是「分两步、先补结构半边」；已按 Jay 裁定锁定。）** |
| D8 | **机制路线**（2026-09-14 grilling 裁定） | **整页快照（memento）**：每次用户动作前对「页面状态」做深拷贝入栈，`Ctrl+Z` 恢复该快照（前端算 diff + 落库）。<br>**理由**：它靠**状态**而不靠**枚举动作** —— 权威状态是扁平 `Block[]`（`blocks.ts:137`，树由 `parent_id` 派生）⇒ 快照即一维数组 + 属性深拷贝；文字粒度**变得免费**（封口时抓一份即可，不必拦 ProseMirror transaction）。<br>**否决 op-log / 反向命令**：两者都要给 `blocks.ts` 那 15+ 个写方法配逆操作，**新增写入路径必漏**（与 ADR-0045 同型病历）。 |

| D9 | **快照的观测点**（grilling 裁定） | **监听权威状态**：对 `blocks` 数组 + 属性表挂监视器（不问「用户做了什么操作」，只问「状态变了没有」），外层加 ~500ms 合并窗口。<br>**理由**：这是唯一**不可能漏**的信号 —— 新增写路径无需任何配合。**否决**「蹭现成的 `structureVersion`」：它是**计数器而非状态**，靠 12+ 处手工自增维护（`blocks.ts:329/336/345/398/622/1049/1215/1246/1327/1343/1400/1436/1566`），且已漏过一次（`useReaderDataChanged.ts:8-26` 注释：`loadPageBlocks` 不 bump，须显式自增否则 UI 不刷新）→ 拿它当观测点等于把「必漏」重新引入（与 D8 否决 op-log 同一个理由）。也否决「挂落库点」（粒度被 300ms / 5s 防抖决定，且「改了还没落库就撤销」抓不到）。<br>**真机实测复核（2026-09-14）**：deep watch 在真实 Vue 代理上**比「轮询 + 去重」更便宜**（84 块 1.8 ms = 一帧 11%，且触发频率被 300 ms 落库防抖封顶）⇒ 维持本裁定、**不改为轮询**；页 **>500 块**时须重估。详见「实测记录」。 |
| D10 | **「复活」原语**（grilling 裁定） | **新增一条显式 Rust 原语**（擦掉 `deleted_at` + 写回 pos / parent）。**理由**：`save_blocks` 现在**完全不碰 `deleted_at`**（`Block.update` 签名里没有该参数，`block_write.rs:56-64`）→「让保存顺手复活」不是改一个分支，而是给保存路径新增一个它现在没有的语义（保存可能意外复活块）；「先物理删再重插」会捅破软删安全网并丢失删除时间。**与 ADR-0047 D2 的回收站共用同一条原语。**<br>**勘误（2026-09-15）**：「同一条」指**原语层** —— 二者共用 `BlockService::undelete`（擦 `deleted_at` + 写回 `pos` / `parent`）；**入口层按用途分装两条**，不是两个原语：撤销走 `executeBatch` 的 `("block","undelete")` arm —— **精确**（只复活快照 diff 明确列出的 id，**不级联**；级联会把「软删但不在快照」的子块一并复活成 stray）；回收站走 `BlockWriteService::undelete_blocks` —— **级联**整棵软删子树。精确版安全的**前提**是 D8 的快照为整页 memento：被级联软删的子块同在删除前的快照里，逐个 id 复活即可覆盖全树。 |
| D11 | **快照的内容边界**（grilling 裁定） | **`blocks`（正文 + 结构 + `format` 含折叠）+ 属性表**。**理由**：属性是用户手动改的数据，不进快照会导致「在属性面板改了 status，按 `Ctrl+Z` 撤不掉」。**否决**含页面级元数据（标题 / 图标）—— 与 D4 第③类冲突，且页面级操作没有「所属页面」这层归属。<br>**且须剔除派生字段**：`Block.renderSegments`（Rust 派生的渲染指令）与 `Block.properties`（属性表的解析副本）**不入快照** —— 二者均可重算，真机实测剔除后体积**省 48.5%**（84 块 44.0 → 22.6 KB）。 |

**推论（随 D1–D11 自动成立，不另立决策）**：

- 「防误操作丢数据」不再由本锚点承接（见 D1）。
- 原始诉求里的「兼容 `Ctrl+Y`」不构成决策点，直接实现。
- `redo` 用标准语义：撤销后一旦发生新的入栈操作，redo 栈立即清空；`Ctrl+Shift+Z` 与 `Ctrl+Y` 等价。
- D2 的「拆掉 TipTap / CodeMirror 内置历史」与 D8 的快照路线**不冲突**：内置历史仍须禁用（否则抢 `Ctrl+Z`），只是文字粒度的采集方式由「拦 transaction」变为「封口时抓状态」。
- **D4 的第②类（派生视图变化）无需特别处理**：折叠存在 `format` 里、属 D11 的快照范围，恢复快照即自动回滚「缩进进折叠父块时的自动展开」。
- **D3 的「结构操作须显式封口」不再需要**：一次结构操作的多次写入落在同一个响应式批次内，D9 的监视器天然只响一次 ⇒ 自动合成一步。

### 机制与寿命的耦合（grill-up 2026-09-14 第二轮：三问重审）

Jay 在 grilling 收尾后重开三问 —— 「① 是否用快照 ② 快照是否落库 ③ 是否取代 block versions」。核查后三问的**所指并不相同**：① 问**机制**（过去的状态怎么表示）、② 问**存储与寿命**、③ 问**产品功能**（用户看得见的那扇门）。这本身是 ADR-0047 D3 命名纪律仍待生效的证据（同一个词三个所指）。

**关键结构性结论：①②不是两问，是同一问。** 「存在哪儿」会反向决定「机制能不能用」—— memento 的定义是「每个动作前存一整页」：存内存只是一次数组拷贝，存磁盘则是**每个动作写一整页 JSON**。⇒ 答「落库」等于同时要求换掉 memento（改走 op-log / diff），而 op-log 正是 D8 已否决的路线。持久化那一列在参数空间里只有两个落点：

| 频率 × 命名 × 存储 | 落点 | 状态 |
|---|---|---|
| 每步 + 匿名 + 落库 | 块版本历史 | **正在下架**（ADR-0047 D1）—— 自动落库必然无限膨胀（保留策略是死代码），匿名必然要按时间切 |
| 少数时刻 + 具名 + 落库 | **Checkpoint（存档点）** | 需求由 ADR-0047 **承接**，地基已在：`SnapshotService::materialize_page`（`snapshot_service.rs:67-94`）已是通用整页序列化（任意 `Page` → `{blocks, properties}`，与 D11 信封同形） |
| 每步 + 匿名 + 落库 的「撤销栈持久化」 | —— | **该格不存在** |

⇒ **「取代」是错框**：Checkpoint 承接的是 block versions 的需求，**memento 谁都不取代**（它在另一格）。唯一还能替「落库撤销栈」说话的动机是**崩溃恢复**，但撤销历史不是数据（数据已落库），丢的只是「还能往回按几次」—— 该判断标为**推测**，非仓库事实。

### 机制落地约束（grilling 2026-09-14 探查所得，观测事实）

1. **不能靠「按原 id 重插」恢复已删块**：Block / Property 都是**软删**（只打 `deleted_at`，物理行仍在：`sqlite.rs:535-537`、`entity/property.rs:249-260`），而 `save_blocks` 的存在性检查 `get_by_id` **过滤 `deleted_at IS NULL`**（`block_write.rs:53`）→ 软删块落入 create 分支 → 裸 `INSERT` 撞 `id TEXT PRIMARY KEY`（`block_write.rs:324-347` 已有测试断言此冲突）。⇒ **恢复必须走「清 `deleted_at`」，需要一条 Rust 侧「复活」原语**（与 ADR-0047 D2 的回收站共用同一条）。
2. **Link 行不必进快照**：link 是 content 的**派生冗余**，`sync_links_for_block`（`block_service.rs:66,116` → `content_parse_service.rs:62-148,264-308`）在块 create / update 时自动重建；删除时 link 是**硬删**（`block_service.rs:134-136`）只能重插 ⇒ 快照信封 = block + properties，与 Ideas `SnapshotContent{blocks,properties}`（`snapshot_service.rs:11-16`）同形。
3. **WASM 的 `execute_batch` 不原子且吞错（落地阻塞项）**：`crates/comind-wasm/src/lib.rs:19-30` 注释直说 "Transaction is the pass-through no-op"，逐 op 错误被吞成 `Null`（`lib.rs:634`）→ 与 tauri 路径（整批回滚，`commands.rs:1243`）**语义不一致**；「恢复 = 一次 executeBatch」在 wasm 路径会留下**半恢复状态且静默**。⇒ 须对齐 tauri 语义。
4. **仓库无可用深拷贝**：`structuredClone` 0 处（`FilterBuilder.vue:31` 注释说明 jsdom 下无法克隆 reactive 代理）、`toRaw` 0 命中；唯一的「快照式」拷贝是 `blocks.ts:1300` 的**浅拷贝**（`format` / `properties` 仍共享引用）⇒ 快照必须自建深拷贝，**不可照抄该处**。
5. **Rust 无「整页树替换」原语**：`block_write.rs` 只有 `save_blocks`（逐块增量 upsert，不删除列表外的块）、`delete_block_cascade`、`delete_page_cascade` ⇒ 快照恢复必须前端算 diff 后落库。

### 实测记录（2026-09-14，真机 tauri-mcp + 本机 Node）

数据源：运行中的 CoMind dev 应用（`workspace-dev/sqlite/comind.db`，6.6 MB）；当前最大页 **84 块**。形状标定用该页真实 block 数据复制到 84 / 252 / 504 / 1008 块。

关键读数：

1. **D9 落地机制（实测复核后修订）**：撤销栈对权威状态的监听，实现上采用**「每页派生签名 watch」**（`useUndoHistory.ts` 的 `blockSig` / `propSig` 对整页块做 `JSON.stringify` 归因，配合 `JSON.stringify` 回声判重去抖），**而非原定的 deep watch**。两者满足同一核心要求——**监听权威状态，故任何新的写入路径自动进栈**（这正是选快照而非 op-log 的收益，见 Consequences）——只是归因手段不同。deep watch 的真机测算（下表）仍成立，但**未采用**：打字期触发频率本就被 300 ms 落库防抖封顶，签名归因的额外 CPU 在 84 块页约 0.6%（与 deep watch 同量级），且**天然规避**了 deep watch 在 >500 块页的退化阈值（见下）。对应 `#107`「勿序列化比较」禁项应**重读**为「禁止把序列化比较作为主 diff 机制 / 禁止轮询式比较」——签名归因式的变更检测不在其内（回声判重是该归因的必要配套）。
   - **退化阈值（签名口径）**：`JSON.stringify` 归因成本随块数线性增长，84 块页约 0.6% CPU；>500 块页需重估（阈值来自外推，真实库无此规模页）—— 标为**推测**。
2. **D11 必须剔除派生字段**：真实块 9 个自有键中，`renderSegments`（Rust 派生）与 `properties`（属性表解析副本）是**可派生冗余**；84 块中 80 块带此二者。剔除后 44.0 → 22.6 KB（**省 48.5%**）。
3. **体积**：slim ≈ **270 B/块**，与页大小无关 ⇒ 峰值 = 步数 × 块数。
4. **附带真机确认（ADR-0047）**：`BlockVersion` 表 **7028 行** / 2256 块，`source` 仅 `auto`(7023) + `restore`(5)，`message` **全为 NULL** ⇒ ADR-0047「自动在跑、手动存档与备注从未接线、只增不减」已由真机数据确证（不再是推测）。

**口径声明**：上表为真机取数，但 block 形状标定用的是**该页数据的复制**（真实库中不存在 >100 块的页）；「deep 占一帧」为计算值，未含真实 DOM 渲染开销。

## Consequences

- `Ctrl+Z` 从「焦点决定谁处理」的不确定态，收敛为**一个接口、一个栈、一个粒度**。
- 代价：TipTap / CodeMirror 的内置历史必须**一次拆干净**（D7 拒绝分阶段），因此这项改动**不能拆成可以独立交付的两半** —— 中间态在用户看来会比现状更糟（两个栈互相抢）。
- 机制代价（D8）：快照的**内存占用** + **恢复要自建 diff**（因约束 5）+ **必须自写深拷贝**（因约束 4）。
- 新增路径的纪律**由结构保证、不再依赖人**：D9 监听权威状态，故任何新的写入路径自动进栈（这正是选快照而非 op-log 的收益）；视图状态变更按 D4 三分法归位（不得一刀切）。
- 术语纪律：「快照」只指 ADR-0042 的 Ideas 物化快照；撤销历史一律用 **History Stack / 撤销历史栈**（ADR-0047 D3）。
- **机制与寿命不可分离**：D5 的「不落库」不是保守取舍，而是 memento 得以成立的前提（见「机制与寿命的耦合」）。任何将来「顺手把撤销栈落库」的提案，都等价于**换机制**，须重走 D8。
